# Working on the Ende docs

This repository builds [docs.ende.sh](https://docs.ende.sh), a static site
generated by [satz](https://jsr.io/@ende/satz) on [Ende](https://ende.sh). This
file lays out the ground rules for agents and contributors making changes. For
the full developer guide see [README.md](./README.md).

## Project layout

Content lives in a few top-level folders:

- `runtime/` - Ende CLI and runtime docs
- `examples/` - the [Examples](https://docs.ende.sh/examples) section
- `lint/rules/` - one page per lint rule
- `ai/` - an entrypoint for LLMs and agents

Pages are GitHub-flavored Markdown; callouts are GitHub alerts (`> [!NOTE]`),
with an optional title after the marker. Left navigation for each section is
configured in the `_data.ts` file in that section's directory (for example
`runtime/_data.ts`).

CLI commands each get a reference page under `runtime/reference/cli/`. The API
reference (`/api`) isn't built at the moment; it will be generated with
`ende doc`.

## Before you open a pull request

Run these locally and make sure they pass:

```console
ende fmt          # format markdown, TypeScript, and JSON
ende lint         # lint the codebase
ende task test    # frontmatter and sidebar tests
ende task check   # type-check the site's code
```

The build must also succeed, with every internal link resolving:

```console
ende task build && ende task check:links
```

Open small fixes as pull requests against `primary` directly. For larger
changes, file a GitHub issue first to get feedback on the shape before writing
the docs.

## Content rules

These are enforced in review and, where noted, in CI.

### Keep `last_modified` fresh

Every content page carries a `last_modified: YYYY-MM-DD` field in its
frontmatter. Whenever you change a page, bump that date to the day of the change
in the same pull request. CI enforces this: `frontmatter_test` checks that every
page has a valid `last_modified`, and the Freshness workflow fails when a page
is edited without bumping it. Check your branch with:

```console
ende task check:freshness
```

### Guides teach, reference enumerates

A topic's depth lives in exactly one place. Guide pages (like `/runtime/test/`)
teach the opinionated path with minimal flags and link out for detail. Reference
pages (under `/runtime/reference/`) enumerate every flag, field, and option.
Don't repeat flag documentation in a guide: link to the reference instead. A
guide may include at most one summary table when it links to the full reference.

### Mark version-specific behavior

When documenting behavior that was added or changed in a specific Ende release,
say so where it's documented: a note callout titled with the release
(`> [!NOTE] Ende 2026.10.17`) for a change worth a callout, or an inline "(Ende
2026.10.17+)" for a brief mention. Releases are ChronVer dates. Don't mark
behavior that predates Ende's first release (2026.10.14).

### Formatting and prose style

- Run `ende fmt` before committing. Generated content and hand-written prose
  both need to pass formatting; wrap long lines so they survive the format step.
- CLI command page titles must be exactly the command name (for example
  `ende run`); put descriptions in the `description` frontmatter field.
- Frontmatter titles must not contain backticks.
- Prefer plain sentences and colons over em-dash joins.

## Examples

Examples in `examples/scripts/` are single TypeScript files, no more than 50
lines, self-contained, and runnable with only Ende builtins and the standard
library. Each starts with a JSDoc comment carrying `@title`, `@difficulty`,
`@tags`, `@run`, and `@group` pragmas. Introduce at most one or two concepts per
example and keep the code easy to read. See the Examples section of
[README.md](./README.md) for the full pragma reference.
